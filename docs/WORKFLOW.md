# 프로젝트 운영 규칙

## 시작과 재개

프로젝트 ID별로 원자료·초안·근거·결재·결과를 나눕니다. 사용자에게 받은 목표, 독자, 결과물, 시간/범위 제약을 brief.md에 씁니다. 완료 기준은 관찰 가능한 결과로 정합니다. 예: “핵심 주장에 원문 연결”, “계산을 입력 데이터로 재현”, “성과 문구가 경험 기록과 일치”.

현재 상태는 DB와 파일이 기준입니다. resume.md는 짧은 안내이며 사실 근거나 결재를 대신하지 않습니다. 입력이 갱신되면 변경된 근거와 관련 결론부터 재검토합니다. 서로 다른 프로젝트는 사용자가 공유하도록 지정한 자료만 연결합니다.

## 위임

팀장은 프로젝트 경로, 작업 ID, 질문, 입력 파일/근거 ID, 담당 출력 파일, 완료 기준을 전달합니다. 원문은 저장하고 필요한 부분만 읽게 합니다. 조사 결과 요약만으로 검증을 끝내지 않습니다.

`task-start`는 기록이지 실제 에이전트 호출이 아닙니다. 이어서 호스트의 하위 에이전트 도구를 호출해야 합니다. 끝나면 실제 결과에 맞춰 completed/failed/cancelled를 기록합니다. 팀장만 DB를 갱신해 기록 충돌을 줄입니다. 파일별 작성자를 나누고 다른 검토자의 첫 판정은 공유하지 않습니다.

독립 검증에 쓸 별도 에이전트를 호스트에서 사용할 수 없다면 순차 재검토라는 한계를 밝힙니다. 반복 역할 연기를 독립 검증으로 부르지 않습니다.

## 결과물 완성

1. 조사자와 작성자는 원문과 초안을 work에 준비합니다.
2. 독립 검증자가 근거 기록과 반대 근거 점검을 반환합니다. 팀장이 등록합니다.
3. 중요한 문제를 수정한 뒤 기본 한 차례 재검토합니다. 중요한 쟁점이 남으면 추가 검토의 필요성과 예산을 판단합니다. 자동 무한 반복하지 않습니다.
4. 팀장은 snapshot과 활성 근거를 최종 결정권자에게 전달합니다. 결재 대상 초안은 work에 둡니다.
5. 결정권자는 근거별 사용 방법, 이견, 조건과 결론을 반환합니다. 보류·기각도 완성된 결정일 수 있습니다.
6. 편집자는 outputs에 읽기 쉬운 결과물을 작성합니다. 작성자와 다른 검토자가 결재된 초안과 비교해 의미·수치·불확실성·근거 사용을 확인합니다. 코드 작성 없는 연구도 해당됩니다.
7. 팀장이 editorial 기록을 등록하고 check를 실행합니다. 통과해도 진위 보증이라고 쓰지 않습니다.
8. 최종 결과물과 한계, 필요한 경우 다음 행동을 전달하고 짧은 resume.md를 남깁니다.

중간 결과를 보고할 때는 완성본으로 표시하지 않습니다. 예산·접근 제한으로 끝난 작업은 확인한 범위와 미완료 사항을 명시합니다.

## 기록의 변경

근거와 결재 기록은 덮어쓰지 않습니다. 근거 수정은 새 ID와 supersedes로 기존 활성 ID를 대체합니다. 결재와 편집도 새 ID로 기록합니다. 과거 이력은 유지됩니다.

결재 후 inputs/work/brief/근거 기록이 바뀌면 기존 결재는 유효하지 않습니다. 최종 파일만 바뀌었다면 새 편집 검토가 필요합니다. 파일 해시 검사는 내용 의미를 이해하지 않습니다. 의미 변경 시 작업자는 반드시 초안과 결재부터 갱신해야 합니다.

## 비용과 실패

정확한 전체 토큰 상한을 강제하려면 호스트 사용량 이벤트를 받는 별도 실행기가 필요합니다. 이 버전은 앱이 팀을 실행하며 작업 등록/기록 한도와 운영 지침으로 범위를 제한합니다. 설정을 우회한 호출까지 막지 않습니다.

실패한 작업은 failed로 종료하고 원인·성공한 단계·재개 조건을 기록합니다. 중단된 실행은 상태를 확인한 뒤 running 작업을 cancelled로 종료합니다. 측정되지 않은 토큰을 추정값으로 채우지 않습니다. 단순 자동 이벤트 기록에 별도 AI 호출을 쓰지 않습니다.
